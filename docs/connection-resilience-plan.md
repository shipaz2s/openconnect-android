# План: обнаружение разрыва и автоматическое переподключение

Статус: этап отслеживания underlying network и отображение reconnect реализованы
в `v1.13-split`. Клиент не навязывает DPD, если сервер его не объявил; дальнейшие
DPD/backoff-этапы отложены.

## 1. Проблема

После неожиданной перезагрузки VPN-шлюза или смены underlying network
(например, Wi-Fi на мобильную сеть) Android продолжает показывать VPN как
подключённый, хотя рабочий туннель уже отсутствует. Пользовательский TUN
остаётся установленным, а Java-слой не получает надёжного признака живого
соединения.

Это две связанные, но технически разные ситуации:

- изменение или временная потеря underlying network должно немедленно запускать
  переподключение через уже существующий механизм `LibOpenConnect.pause()`;
- «чёрная дыра» без события Android должна обнаруживаться протокольным DPD и
  таймаутами libopenconnect.

Существующая реализация решает их не полностью:

- `DeviceStateReceiver` использует устаревший `CONNECTIVITY_ACTION`,
  `getActiveNetworkInfo()` и сравнивает только `NetworkInfo.getType()`;
- смена одной Wi-Fi сети на другую и часть переходов на современных Android
  могут остаться незамеченными;
- DNS `KeepAlive` предназначен для поддержания активности, но отсутствие DNS-
  ответа не считается отказом и не вызывает reconnect;
- UI остаётся в `CONNECTED`, пока native mainloop пытается восстановиться или
  бесконечно ждёт при отсутствии эффективного DPD.

## 2. Цель и ожидаемое поведение

- При смене используемой физической сети активное VPN-соединение автоматически
  переподключается без действий пользователя.
- При временном отсутствии сети VPN ждёт её восстановления, не создаёт цикл
  быстрых попыток и переподключается после появления валидированной сети.
- При «молчаливой» потере шлюза разрыв обнаруживается за ограниченное,
  документированное время и запускается штатный reconnect libopenconnect.
- Во время восстановления UI и уведомление не должны утверждать, что туннель
  полностью работоспособен.
- После исчерпания допустимого времени восстановления сервис переходит в
  `DISCONNECTED` с диагностируемой причиной, а не остаётся ложноподключённым.
- Поведение одинаково для обычного VPN и per-app allowlist; TUN и allowlist
  переустанавливаются только если это действительно требуется.
- Сохраняются `minSdk 23`, работа IPv4/IPv6 и split tunneling по приложениям и
  подсетям.

## 3. Принципы реализации

1. Сначала использовать штатные механизмы Android и libopenconnect.
2. Не определять здоровье VPN по доступности публичного сайта или DNS.
3. Не запускать второй параллельный management thread.
4. Сериализовать pause/resume/reconnect/stop и устранять гонки событий сети.
5. Добавлять native-изменения только после воспроизводимого доказательства, что
   Java/JNI API текущей libopenconnect недостаточно.
6. Ограничивать частоту reconnect с debounce/backoff, но быстро реагировать на
   реальную смену underlying network.

## 4. Этап 0 — воспроизведение и наблюдаемость

До исправления собрать логи текущего поведения для четырёх сценариев:

1. Wi-Fi → мобильная сеть без промежутка offline.
2. Wi-Fi A → Wi-Fi B (тот же transport).
3. Потеря сети → восстановление той же сети.
4. Шлюз становится «чёрной дырой»: пакеты отбрасываются без FIN/RST.

Для каждого сценария зафиксировать:

- Android API level, модель устройства, протокол VPN, DTLS on/off;
- события `ConnectivityManager`, transport, `Network` identity и capabilities;
- сообщения libopenconnect о DPD, CSTP/DTLS и reconnect;
- время последнего RX, обнаружения отказа, начала и окончания reconnect;
- `adb shell dumpsys connectivity`, `dumpsys vpn` и релевантный `logcat`.

Добавить структурированные, но не содержащие адресов/учётных данных сообщения:
`uplink lost`, `uplink available`, `uplink changed`, `reconnect requested`,
`native reconnected`, `reconnect failed`.

Результат этапа — короткий тестовый отчёт и подтверждённая причина каждого
сценария. Нельзя начинать с произвольного watchdog-интервала без этих данных.

## 5. Этап A — современное отслеживание underlying network

Заменить основную логику `CONNECTIVITY_ACTION` на
`ConnectivityManager.NetworkCallback`.

- Для API 23+ отслеживать сети с `NET_CAPABILITY_INTERNET` и без
  `NET_CAPABILITY_VPN`.
- Хранить identity текущей пригодной underlying network, а не только transport.
- Учитывать `onAvailable`, `onLost`, `onCapabilitiesChanged` и при необходимости
  `onLinkPropertiesChanged`.
- Сеть считать пригодной после появления нужных capabilities; требование
  `VALIDATED` проверить на корпоративных сетях и captive portal, прежде чем
  сделать обязательным.
- При краткой перестановке callback-событий применять небольшой debounce.
- Смена `Network` при активном соединении вызывает один `reconnect()`.
- Полная потеря сети вызывает pause; появление сети — resume с последующим
  штатным reconnect.
- Старый broadcast оставить только как fallback, если реальный тест выявит
  устройство/API, где callback недостаточен; не обрабатывать одно событие
  дважды.
- Рассмотреть `VpnService.setUnderlyingNetworks()` после выбора сети. Включать
  его только если тесты подтвердят пользу и корректный возврат к автоматическому
  выбору Android.

Трекер сети вынести в тестируемую state machine, не связанную напрямую с
`BroadcastReceiver`.

Предлагаемый коммит:
`fix: track VPN underlying network changes`.

## 6. Этап B — корректная модель состояния и reconnect

Расширить внешнее состояние минимум состоянием `RECONNECTING` либо отдельным
признаком деградации. Переходы должны быть однозначными:

```text
CONNECTED
  ├─ uplink lost ───────────────> WAITING_FOR_NETWORK
  ├─ uplink changed ────────────> RECONNECTING
  └─ DPD/CSTP failure ──────────> RECONNECTING

WAITING_FOR_NETWORK
  └─ usable uplink available ───> RECONNECTING

RECONNECTING
  ├─ native reconnect callback ─> CONNECTED
  └─ terminal failure/stop ─────> DISCONNECTED
```

- Реализовать `LibOpenConnect.onReconnected()` в `AndroidOC` и обновлять UI
  только по фактическому callback native-библиотеки.
- Не менять состояние на `CONNECTED` только из-за наличия TUN.
- Сделать запрос reconnect идемпотентным: несколько Android-событий дают один
  `pause()` на native mainloop.
- Явно различать пользовательский stop, ожидание сети, автоматический reconnect
  и терминальную ошибку.
- Проверить жизненный цикл `ParcelFileDescriptor`: при внутреннем reconnect
  libopenconnect существующий TUN остаётся; при полном перезапуске соединения
  новый Builder повторно получает app allowlist и маршруты.

Предлагаемый коммит:
`fix: expose reconnecting VPN state`.

## 7. Этап C — обнаружение «молчаливого» шлюза

Сначала проверить штатный DPD текущей libopenconnect:

- какие DPD/keepalive значения присылает каждый поддерживаемый сервер;
- действует ли профильный `dpd_override` одновременно для CSTP и DTLS;
- срабатывает ли `ka_stalled_action()` при полном drop входящего трафика;
- укладывается ли `mainloop(300, RECONNECT_INTERVAL_MIN)` в ожидаемое время;
- не маскирует ли DNS `KeepAlive` проблему и не создаёт ли ложную видимость
  активности.

Если сервер не задаёт DPD, определить безопасную политику клиента:

- предпочтительно установить документированный DPD по умолчанию для активного
  соединения, сохранив профильный override;
- интервал должен быть консервативным и учитывать Doze/сон, чтобы не вызывать
  reconnect только из-за задержки планировщика;
- пользовательский DNS `KeepAlive` не использовать как health check.

Только если штатный DPD невозможно надёжно применить через существующий API,
добавлять минимальное JNI/native-изменение: получить время последнего принятого
пакета/состояние reconnect или явно разбудить mainloop. Не реализовывать
параллельный TCP/HTTP probe к шлюзу без отдельного обоснования.

Предлагаемый коммит:
`fix: detect stalled VPN peers with DPD`.

## 8. Этап D — backoff и защита от циклов

- Первая попытка после смены сети — немедленная.
- Повторные неуспешные попытки — exponential backoff с верхней границей и
  небольшим jitter.
- Новая underlying network сбрасывает backoff и разрешает немедленную попытку.
- Пользовательский stop отменяет все отложенные действия.
- Ошибка аутентификации, отозванный сертификат или 401 не должны бесконечно
  повторяться без участия пользователя.
- Не создавать notification/dialog storm.

Если native mainloop уже полностью реализует нужный reconnect timeout/backoff,
не дублировать его в Java; Java-уровень должен лишь отражать состояние.

Предлагаемый коммит:
`fix: bound automatic VPN reconnect attempts`.

## 9. Автоматические тесты

Локальными тестами покрыть state machine:

- первый доступный uplink не вызывает лишний reconnect при старте;
- Wi-Fi → cellular вызывает ровно один reconnect;
- Wi-Fi A → Wi-Fi B вызывает reconnect при одинаковом transport;
- краткие `onLost(A)` после `onAvailable(B)` не переводят систему обратно в
  offline;
- потеря всех сетей вызывает pause, появление сети — resume/reconnect;
- повторяющиеся callbacks дедуплицируются;
- stop во время debounce/backoff отменяет reconnect;
- `onReconnected()` возвращает состояние `CONNECTED`;
- terminal native error переводит в `DISCONNECTED`;
- per-app allowlist не теряется при полном перестроении TUN.

Минимальные проверки перед интеграцией:

```bash
./gradlew testDebugUnitTest --no-daemon
./gradlew lint --no-daemon
./gradlew assembleDebug --no-daemon
```

## 10. Ручная матрица

Проверить Android 6 и современную версию, соответствующую targetSdk:

| Сценарий | Ожидаемый результат |
|---|---|
| Wi-Fi → 4G/5G | Один reconnect, трафик восстанавливается |
| 4G/5G → Wi-Fi | Один reconnect после пригодности Wi-Fi |
| Wi-Fi A → Wi-Fi B | Смена `Network` обнаружена |
| Airplane mode 30–120 с | Ожидание без цикла, затем восстановление |
| Сервер drop без FIN/RST | DPD обнаруживает отказ в заданный срок |
| Сервер reboot | Автовосстановление после доступности сервера |
| DTLS включён/выключен | CSTP и DTLS корректно восстанавливаются |
| Экран выключен / Doze | Нет ложных reconnect storm |
| IPv4 и IPv6 | Трафик восстанавливается по обоим стекам |
| Split routes | Маршруты сохраняются после reconnect |
| Per-app allowlist | Только выбранные приложения используют VPN |
| Always-on VPN | Состояние и восстановление корректны |
| Неверный пароль/401 | Нет бесконечного автоматического входа |

Для каждого теста измерить время обнаружения и полное время восстановления.

## 11. Риски

- `VALIDATED` может отсутствовать у рабочей корпоративной сети: не делать его
  безусловным до тестирования.
- Android callbacks могут приходить не по порядку: state machine должна
  учитывать множество сетей, а не один boolean.
- Слишком агрессивный DPD расходует батарею и даёт ложные разрывы в Doze.
- Слишком долгий DPD оставляет ложный `CONNECTED`.
- Повторный `establish()` может кратко создать утечку или потерю маршрутов;
  предпочитать внутренний reconnect с тем же TUN.
- Автоматический reauth может потребовать пользовательский ввод; UI должен
  корректно перейти в `USER_PROMPT`.
- Изменение native-кода повышает стоимость сопровождения; оно допускается
  только при подтверждённом недостатке существующего JNI.

## 12. Критерии приёмки

- Все четыре исходных сценария воспроизводятся до исправления и проходят после.
- Смена identity underlying network обнаруживается независимо от transport.
- «Молчаливый» сервер обнаруживается за согласованный предел времени.
- UI не показывает обычный `CONNECTED` во время ожидания/reconnect.
- Нет параллельных management threads и reconnect storm.
- Пользовательский stop и ошибки аутентификации не перезапускаются самопроизвольно.
- Per-app allowlist, split routes, DNS, IPv4/IPv6 и minSdk 23 не регрессировали.
- Unit tests, lint и debug build проходят; ручные результаты зафиксированы.

## 13. Предлагаемая последовательность

1. Отдельный диагностический коммит и отчёт воспроизведения.
2. Network callback + тестируемая state machine.
3. Состояние `RECONNECTING` и обработка `onReconnected()`.
4. Проверка и настройка DPD на основании измерений.
5. Backoff только там, где его не обеспечивает libopenconnect.
6. Полная ручная матрица и release notes.

Первый implementation slice следует ограничить этапами 0 и A. Это даст
надёжную обработку смены адаптера без преждевременного вмешательства в native-
код. Решение по DPD принимать после логов сценария «чёрная дыра».
